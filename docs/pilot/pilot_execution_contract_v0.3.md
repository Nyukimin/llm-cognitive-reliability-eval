# 次工程へ渡す実装・採点条件

版：pilot-contract-0.1／Stage 1 v0.3／2026-09-21

これは要求仕様v0.5を変更する文書ではなく、二者レビューを踏まえた制作上の実装条件である。設計として定めたことと、実環境で検証できたことを区別する。対応する機械可読台帳は `implementation_contract.json`。ここに示す対照は判定設計の検査項目であり、正式Fullのケース本文でも、Short問題集でもない。

## 1. P-M：別セッション情報利用の観測境界

### 記録

製品・モデル・API等の区分とは独立に、`trace_visibility`を`none`、`partial`、`declared_interface_complete`で記録する。最後の値も、明示した外部インターフェースの記録範囲を意味し、製品内部をすべて観測したことにはしない。`trace_scope`と証拠IDを付ける。

`retrieval_result`は、返却内容あり／空／実行エラー／不明を区別する。保存元情報の存在、読み出す権限、取得処理の実行、生成時入力への到達は別の事実である。`target_delivery`は到達確認／未到達を確認／不明を区別し、到達・未到達には観測根拠を要求する。取得ツールの応答だけでは、その後の入力への組込みまで確定しない。

### 採点と集計

課題の端点出力の成否と、観測可能な段階別結果を別欄にする。ログ非公開の環境でも、課題自体の成立と必要証拠を確認できた場合は製品全体の結果を記録できる。ただし「取得したが推論を誤った」「取得しなかった」とは断定しない。モデルの自己申告や回答の正誤から取得を証明しない。

十分な情報が対象入力へ到達したことが確認できても、報告できるのは、例えば「入力到達が確認された条件で、支持される回答を生成できなかった」までである。それだけで内部の読解、注意、推論等の単独原因を特定しない。資料の信頼性を検討すべき課題と、与えられた設定に従う課題は従来どおり分離する。

段階別の率は観測群を分ける。共通端点を集計する場合は対象集合・集約法・観測群別内訳を事前定義し、原因指標へ読み替えない。試験者が同じ証拠を直接入力する対照は別のR/Dケースとして登録する。その差だけで元の非公開取得経路が原因だったと証明したことにはしない。

### 完了に必要な実物

Q04で、非観測、取得結果のみ、入力到達確認の各アダプター記録例と正常対照を検査する。Q05で観測群・用途別分母・欠落時利用範囲を固定する。現時点では実アダプターは未検証。

## 2. P-T：実ツールと文章シミュレーションの区別

Tの必要条件は、対象LLMの文章と独立した実行器・状態・操作記録・状態検証である。試験用データが架空であることは問題ではない。モデルが「実行した」と書いただけの状態を、実行済みの証拠にしない。

初期はAPI/ローカルから接続する隔離実行器を予備実装の候補にする。原試験の状態・許可操作・分岐・採点と対応付け、命令、戻り値、エラー、前後状態、検証器版を保存する。人手仲介によって本当に隔離実行器を動かす場合も、仲介手順と介入記録を別条件として検証する。

Web製品でも、同等の隔離環境と証拠を確認できればT候補にできる。特定製品が対応済みとはここで認定しない。テキストだけのツール役、LLMが生成した架空の実行ログ、保存ログの読解はR/Dへ区分し、Tの成績へ混ぜない。変換した課題は新たな派生ケースとしてFullで受入れる。

許可されない外部書込み、本物の秘密情報、普段使いのデータへの副作用は禁止する。Tが使えない環境は適用範囲・未実施として報告し、黙って読解版へ代替しない。事前に課題の対象にしたツールの障害は、実行状態と達成・報告の各判定を分けて残す。

Q04で原環境との対応、成功・失敗操作、文章模擬との区別を検証する。Q05で公開対象の経路と非対応時の手順を確定する。B03のユーザーへの情報要求を行動とするDの案は維持する。

## 3. P-A：B01とB14を同時に誤判定しない

「一方の能力を優先すれば他方が下がる」という構造を採点へ組み込まない。適用条件を要件IDごとに決める。有効要求、すでに分かる条件、決まっていない条件、許された仮定、次に許容される行動を参照表へ記録する。

| 入力と行動の関係 | 判定の扱い |
| --- | --- |
| 重要な条件が不足し、必要な確認をしながら既知の目的・制約を保持する | 課題完了は保留でもよい。確認したことだけでB01失敗にしない。B14はその確認の必要性で評価する。 |
| 条件不足への確認は正当だが、別の既知要件を落とす | 確認に関するB14成功で、既知要件のB01違反を免除しない。 |
| 必要情報がすでにあるのに同じことを質問し直す | 正常な保留として一律に保護しない。B14と当該要件への影響を別に評価する。 |
| 複数の害のない選択肢、または許可された仮定で進める | 確認しなかったことだけで失敗にしない。仮定の扱いと実際の要件充足を照合する。 |
| 不明な条件を確定した事実として補い、完了したと報告する | 見かけの完了を要件達成の代用にしない。B14、必要に応じB12等の根拠を分けて記録する。 |
| 試験側の資料が欠け、適切な行動を判定できない | モデルの失敗を推定せず、採点不能または当該項目の適用保留とする。 |

同じ回答をB01/B14等でタグ付けしても独立試行は増えない。B14の成功はB01の自動合格でもなく、課題未完了はB01の自動失敗でもない。B07/B08との重複整理はQ03から削除しない。

Q03で参照表と反例を固め、Q04で採点に適用する。O02は引き続きB14の探索候補であり、今回の規則追加によって過去の失敗を確定した扱いにはしない。

## 4. P-U：中断状態の提出を軽くする

低負荷化は採用するが、一般参加者の離脱率が高い・対策で下がった、という実測はない。目的は、状態だけでも残せる経路を作り、選択的提出の程度を把握できる範囲を増やすこと。

同意済みの参加者について、試行ID、ケース版、判明している環境情報、未開始／開始／中断／完了の状態を、理由の自由記述や全文ログなしで送れる候補UIを設計する。ログ提出は別に選択・確認できるようにする。生ログの自動送信、秘密情報の送信、同意確認の省略を「1クリック」のために導入しない。

開始が観測されていない未提出者について、開始・中断・成否を推測しない。ページを閉じることが観測可能と仮定しない。試行IDで再開・重複を対応付け、状態報告だけの提出を採点可能な応答として数えない。分母は既存の用途別ルールを維持する。

Q05で試作、欠落・重複・同意拒否の検査、保管範囲を確定する。まだフォームも追跡機能も実装・公開していない。

## 5. P-J：B11の意味的退行を重点監査する

B11を採点の重点監査対象にする理由は、今回の目的との関係と判定の難しさを考慮した設計判断であり、他領域より誤判定率が高いと測定したわけではない。「他領域より厳格」という曖昧な条件だけを置かず、検査対象を具体化する。

旧成果物、当時有効な要求、正当な変更・撤回、修正後成果物を保存し、要件ごとの変更台帳を作る。台帳には要件ID、時点、旧根拠、変更要求、依存関係、新根拠、判定の許容範囲を付ける。単語が消えたことだけを意味の消失としない。

検証には、意味を保った言い換え・統合、実際の要件欠落、正当な削除・撤回、誤りは直ったが依存箇所が残る例、証拠不足の境界例を含める。機械判定できる部分は規則・実行結果で検証する。意味的部分では、人手による根拠照合を含む参照ラベルと比較し、正常を失敗にした誤陽性、退行を見逃した誤陰性、判定保留を別報告する。

同じ出力の反復採点による揺らぎと、異なるモデル出力の揺らぎを分離する。人同士・LLM同士の一致だけで正解としない。不一致は元記録へ戻して判断し、未解決なら判定保留。別LLMのレビューをHuman評価と数えない。

Q06で、対象層・監査件数・許容誤判定・人手参照の作成者と担当を正式採点前に定める。閾値は結果を見て都合よく変えず、変えた場合は版更新と影響対象の再採点・追加の未使用検証を行う。現時点では人手参照担当は未割当、検証は未実施。ルミナが必要資料を用意するが、人手検証の完了を代行したと報告しない。条件が満たせない意味採点は試作・暫定分析までに限定し、正式な検証済み得点として公開しない。

## 6. 次工程の進め方と検証状態

Q01/Q02の個別ケース精査は、上記のアダプター・UI・意味採点が完成する前から進める。既存ケースの直接適合性、ライセンス、原版・採点実装、手動経路の候補件数を調べる。FullからShortを抽出する順序を維持する。

Q03で適用・除外の判定表、Q04でケースとアダプターの予備実行を行う。Q05のうち安全・同意・最低記録など予備実行にも必要な条件は、その実行前に先行して確定する。正式収集前には残る公開・保管・分析条件を固定する。Q06は正式なケース／採点の受入れ前に実物で検査する。

現時点で実施した検査は、文書・台帳の整合、参照、変更範囲、ポリシー項目の存在・禁止組合せの検出である。対象LLMの挙動、実ツールアダプター、メモリ取得、収集UI、Human照合の検証結果ではない。
